# pr-review-merge reference: step 6, report back

Moved verbatim from `SKILL.md` by ugcportal-j13u. The checklist in `../SKILL.md` is what a round follows; this file holds the rationale, catalogued incidents and worked examples behind it, and where the two differ, this text is the rule. The commands, templates, tables and headings the checklist carries verbatim are not repeated here; an italic line marks where each one stood. "Above", "below" and "this file" in the moved text refer to the original single file: read them as earlier or later in the same step, in the checklist or in this reference.

State plainly:

- PR number and decision (merged / left for human), with the exact reason.
- **The review round number and the chain status (`exact` / `approx` / `broken`)** — for a bootstrap, which of the three sources the starting number came from, whether the clamp applied, and that you stamped `B + 1`; for `approx`, *why* it is approx (bootstrap, reset, or self-asserted because the reviewer is the PR's author); for `broken`, which integrity check failed and which comments were involved.
- **The model this round ran on and why (ugcportal-1mhn):** the `model=… effort=… reason=…` line the orchestrator got from `node scripts/reviewer-model.mjs <pr-number>` before spawning you (it is in your brief), or, when the script exited 2 or the brief names none, the model you ran on and the orchestrator's recorded reason. Write it as the `Model: <tier> (<reason>)` line both step 5 templates carry.
- **That you released the step 1a lock**, or — if you stood down — that another run held it and you consumed no round, posted nothing and stamped nothing.
- If step 5's merge-readiness read stopped the run (a `mergeStateStatus`/`mergeable` value that is not `CLEAN` or `BEHIND`, `UNKNOWN` twice, or `CLEAN` with a head other than the reviewed one): the value read (and, for the head case, both heads) and that the follow-up comment was posted.
- If `gh pr merge` was refused for any reason (not mergeable, squash refused, or `--match-head-commit` refused because the head moved), or `squashMergeAllowed` was false: the error (or the `squashMergeAllowed` value) quoted, that the follow-up comment was posted and that the lock was released.
- If the merge went through step 5's BEHIND recovery: the reviewed head, the new head after the update, and the diff-check result (`empty`, or non-empty with the run ending there) — or which stop of the recovery ended the run, and that the follow-up comment was posted.
- If this run stopped before step 4 (CI, mergeability, base branch), say so and that it was stamped with a **non-counting** stop marker, so it is clear no round was consumed.
- If this was round 7+, that it was a post-escalation verification round (step 5b), and the three things that let you enter that row: the chain was `exact`, the URL of the **latest** stop comment at or above 6, and the changed head SHA or non-bot human comment since it.
- **All four recurring families from step 4.1, named, each with what it found (including "nothing").**
- **Step 4.2**: the `<!-- ugcportal-fix-wake: … -->` line exactly as you posted it — so `since` and `changed` are in the report whether or not the trigger fired — and, if it fired, the terms grepped, the hit count, and the verdict per hit, "0 falsified" included.
- **Step 4.3**: whether this round did the whole-file read or which earlier round's marker covers it, and the per-file verdicts if it was this round's.
- **Step 4.4**: the `<!-- ugcportal-measured: … -->` line exactly as you posted it, so the head and the baseline are in the report whether or not the trigger fired — and, for every delta you report anywhere in this round, the baseline figure and the command that produced it, measured by you on the same tree; for every absence, the path and the commit you read it at.
- Findings with **the severity you assigned each one** (step 4's angles don't produce one on their own — see step 4's closing paragraph), and which were fixed versus deferred.
- Bead ids filed in step 5a, if any — **each with the `discovered-from` edge you read back beside it**, in the direction it points, not just the id.
- A findings list the orchestrator can turn into `findings_r<N>` (step 4a item 5): each finding with its family from step 4.1 (a finding may name two) and its severity, or a statement that the round was clean.
- The `tokens_qa` figure and the `cost_ite_qa`/`cost_calls_qa` figures recorded in step 4a (or note that they were skipped, and why), and whether `bd-verify-metadata` confirmed they landed. "Recorded" without a read-back behind it is the claim, not the evidence.

**If the PR was left for a human at the sensitive-path reviewed-clean stop (step 2), say so and give the orchestrator the bead instruction (ugcportal-ub7y).** A stop with a blocker, including the round-6 escalation, is not reviewed clean: no label, and a label already there is removed under step 2's removal rule. The `approx`-at-cap and `broken`-chain zero-finding stops are not labelled for their chain state (ugcportal-osth); step 2 gives the precedence when such a stop is also a sensitive-path one.

- The GitHub label `needs-human-merge` is on the PR (you applied it; quote the `gh pr edit` output or `gh pr view <n> --json labels`), and the orchestrator runs, from the main checkout, `bd label add <bead-id> stalled-on-human`.
- Removal when a later round blocks is the reviewer's, per step 2's rule. After the PR has merged, the orchestrator removes both when it closes the bead under `CLAUDE.md` Session Completion step 3: `gh pr edit <n> --remove-label needs-human-merge` and `bd label remove <bead-id> stalled-on-human`. No `pr-review-merge` run takes place after a human merges by hand, so this reviewer-run step cannot do it; until CLAUDE.md's step 3 says so, it is the orchestrator's habit, not a mechanism.
- `node scripts/check-human-merge-labels.mjs` audits the labels on open PRs and prints its counts first (PRs examined, round-reviewed PRs, verdict-marker PRs, sensitive-path round-reviewed PRs, and the four classes). It starts from the round marker, not from the verdict marker alone, so a reviewer who skipped step 2's paragraph is still listed, on a human-authored PR as on a bot-authored one: A is a latest round with the verdict marker and no label; B is a sensitive-path round-reviewed PR with no label and no verdict marker, which is either a blocked round (correct) or a skipped marker, so a human reads its comment; C is a label with no verdict marker in the latest round, or with no round comment by a reviewer at all, a stale label; D is a label with a verdict marker whose round reviewed a different head than the PR's current one (a push since), read from the round's `inline-fix head=<sha>` line when it has one (step 5, "After an inline fix"), else the `at=` of its `ugcportal-measured` line or its `head <sha>`. A round comment counts only when the reviewing account (`gh api user`, `app/` prefix and case ignored) wrote it. The identity source (`gh api user`) is step 4b's, but the handling of another account's marker is not: step 4b reads a round marker by another account as a `broken` chain, while the check ignores such a comment and reads the reviewer's latest round comment; a PR the reviewer opened itself (human-authored, an `approx` chain) still has its round comments counted, and a comment by the bot that opened the PR is not a review. It exits 0 when nothing is listed, 1 when A, B, C or D is listed, and 2 when the reviewer login cannot be resolved or the PR list or a PR's comments or files hit the fetch limit and so a zero could not be trusted. It cannot tell a reviewed-clean PR with a skipped marker from a blocked one; B is where it says so. It reads open PRs only, so a stale label on a merged PR is not caught. It reads issue comments only (`gh pr list --json comments`), not review bodies, which matches where this skill writes its markers (`gh pr comment`); and a PR with 100 or more files, like one with 100 or more comments, exits 2 because a sensitive path past gh's window would be missed.

If merged, confirm the merge actually happened (`gh pr view <n> --json state,mergedAt`) and confirm the result of the scoped sweep above — removed and the final `git ls-remote` check confirms it gone, or kept (naming the reason the script printed) and still present.
