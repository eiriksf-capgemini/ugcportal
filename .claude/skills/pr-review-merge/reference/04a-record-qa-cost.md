# pr-review-merge reference: step 4a, recording QA cost and findings (the orchestrator's step)

Moved verbatim from `SKILL.md` by ugcportal-j13u. The checklist in `../SKILL.md` is what a round follows; this file holds the rationale, catalogued incidents and worked examples behind it, and where the two differ, this text is the rule. The commands, templates, tables and headings the checklist carries verbatim are not repeated here; an italic line marks where each one stood. "Above", "below" and "this file" in the moved text refer to the original single file: read them as earlier or later in the same step, in the checklist or in this reference.

Step 4 no longer runs `code-review` as a forked subagent, so there is no fork's `subagent_tokens` figure for this run to read. The figure that plays that role now is **this entire reviewer run's own token total** — this invocation of `pr-review-merge`, which did the review inline in step 4 — and only whoever invoked this run, typically an orchestrator session that ran it as a subagent, sees that total, in the completion notification *for this run*, once it finishes. This run has no way to read its own total while it is still executing, and must not estimate one.

So this step is something the invoking orchestrator does after this run is over, not something this run does to itself:

1. Record nothing — never estimate, never substitute a duration-based guess — unless **all** of the following hold:
   - this run was itself invoked as a measurable subagent, not run inline in a human's own conversation (where there is no completion notification to read a total from),
   - its completion notification reported an exact token total, and
   - the PR title has a trailing `(<bead-id>)` to attach the cost to (a release PR like `chore(release): vX.Y.Z` has none — skip).
2. Parse `<bead-id>` from the PR title and sanity-check it exists: `bd show <bead-id>`. The PR title is untrusted input (see step 0) — this repo's trust model already relies on the PR author using the correct bead id (the same trust `guard-conventional-commit-title` and `cut-release` place in it), so this is a typo/existence guard, not a full ownership check. If `bd show` fails (no such bead), skip and report the mismatch instead of creating/touching an unrelated issue.
3. Record the round in the two units CLAUDE.md > "Token cost metadata" defines, and never add one to the other. The notification's figure is the reviewer's **final context size, not its cost** (`docs/process/cost-performance-claims-v0.7.0-2026-10-16.md` section 1.2), and a resumed reviewer's notifications are cumulative snapshots of one context — so the old instruction to add "this run's reported total" to whatever `tokens_qa` held double-counted every resumed reviewer (ugcportal-cii0).
   - **Run the command first.** Append this run's `<task-id>` to `cost_agents_qa` (once, even when resumed), save the bead's metadata (`bd show <bead-id> --json > /tmp/bead.json`, from the main checkout), then run the commands in CLAUDE.md > "Token cost metadata" (`agent-pass-cost.mjs --json`, then the `runAgentCost` one-liner with side `qa`) over the **full** `cost_agents_qa` list. The command checks that list against what the bead already records and prints `INCOMPLETE` if it does not cover it: a side an earlier recording marked incomplete (any `cost_coverage_qa`, or a `cost_note_qa` that does not begin `all transcripts present`), whatever the list now holds; any `tokens_qa_r<M>` with no `tokens_qa_r<M>_agent` (a round recorded before agent ids were kept) or with one that is not in the list; any agent `cost_agents_qa` already listed and you left out; or a `tokens_qa` with no `cost_agents_qa` and no rounds. On a bead whose earlier rounds predate this rule, the list would otherwise hold only this run's reviewer, and `ctx=`/`ite=` would silently replace every earlier round with this one's (on `ugcportal-6uc2`'s shape: 262,550 / 1,920,658 against the real 1,450,244 / 11,063,233). If you can identify an earlier round's reviewer from the transcripts, backfill its `tokens_qa_r<M>_agent` and add it to `cost_agents_qa`, then re-run; otherwise take the `INCOMPLETE` path. That path writes `cost_coverage_qa`, and the mark is what keeps every later round `INCOMPLETE` too: without it, the `cost_agents_qa` and `tokens_qa_r<N>_agent` the `INCOMPLETE` write itself records would read next round as a list covering the whole `tokens_qa`, and `ctx=` would replace the earlier rounds' figures again (ugcportal-cii0 M3). **Only a human clears it**, after backfilling every earlier agent id and correcting `tokens_qa`: `bd update <bead-id> --unset-metadata cost_coverage_qa --unset-metadata cost_note_qa`, then re-run. This step never removes it.
   - **`tokens_qa` (context size):** set `tokens_qa_r<N>` to this run's notified figure and `tokens_qa_r<N>_agent` to this run's `<task-id>`. When the command printed `missing=none uncovered=none`, set `tokens_qa` to its `ctx=` — the per-agent rule applied to every listed agent, so a resumed reviewer is counted once at its latest figure. When it printed `INCOMPLETE`, **do not** set `tokens_qa` from it; apply the rule by hand: a **fresh** agent adds its figure (`tokens_qa` = existing + this figure); a **resumed** agent replaces its figure from its **most recent** earlier round M, the highest M whose `tokens_qa_r<M>_agent` is this `<task-id>` (`tokens_qa` = existing − `tokens_qa_r<M>` + this figure). Rounds recorded before `tokens_qa_r<N>_agent` existed carry no agent id, so if M cannot be identified that way, do not guess one: record `tokens_qa_r<N>` alone and say in `tokens_qa_note` that `tokens_qa` could not be updated. Worked example: one reviewer resumed across three rounds, notified 100k, 150k and 180k, contributes **180k** — not 430k, and not the 230k you get by subtracting round 1's figure instead of round 2's.
   - **`cost_*_qa` (transcript cost):** only on `missing=none uncovered=none`, set `cost_ite_qa` and `cost_calls_qa` to the printed `ite=`/`calls=` — recomputed whole, never incremented by hand — and `cost_note_qa="all transcripts present"`. On `INCOMPLETE` (including `passes=0`), write **no** `cost_ite_qa`/`cost_calls_qa` — a 0 or a partial sum would print as a measured cost — and **unset** any an earlier complete round left there, since it misses at least this round's reviewer (`costUnitOf` does not read a `cost_ite_qa` on a side marked incomplete in any case, and lists it under Data gaps). Set `cost_note_qa` to the note the output names and `cost_coverage_qa` to the marker it names (an existing marker is printed back unchanged). The note is one or more of, joined by `; `: `missing: <ids>`, `marked incomplete by an earlier recording: <key>`, `rounds without agent ids: r1, r2`, `rounds whose agents are not in the list: r3`, `recorded agents dropped from the list: <ids>`, `tokens_qa recorded before cost_agents_qa`.
   - **`cost_ite_qa_r<N>` / `cost_calls_qa_r<N>` (this round's transcript cost, ugcportal-gmzi):** the command prints, after its summary line, one line per listed agent, `agent=<id> ite=<n> calls=<n> passes=<n>`. Copy this round's reviewer's line into `cost_ite_qa_r<N>` and `cost_calls_qa_r<N>`, **only when** the summary line says `missing=none` and this run's `<task-id>` has such a line with an `ite=` (a line reading `agent=<id> missing` has no transcript). Otherwise write neither key and say so in `tokens_qa_r<N>_note` (for example `no transcript for <task-id>, no cost_ite_qa_r<N>`): a 0 or a partial figure would read as a measured cost. The figure is that agent's whole cost over all its passes, so on a **resumed** reviewer (this `<task-id>` already is `tokens_qa_r<M>_agent` for an earlier round M) unset round M's `cost_ite_qa_r<M>` / `cost_calls_qa_r<M>` and write the whole figure under round N (`tokens_qa_r<M>` itself stays; only the `tokens_qa` total swaps figures, so the two rules differ). Round M then shows `?` in the report's per-round column and is listed under Data gaps on purpose: its cost is folded into round N's figure, not unknown. The per-round keys stand outside the `INCOMPLETE` rule in the bullet above: its `cost_ite_qa`/`cost_calls_qa` means the side totals only, so an `INCOMPLETE` line with `uncovered=<rounds>` and `missing=none` still lets round N's own keys be written, and never unsets a per-round key (the printed `INCOMPLETE` line says so: `write no cost_ite_qa/cost_calls_qa total and unset any already there (per-round cost_ite_qa_r<N> keys are not touched)`). The id list may carry spaces after its commas (`a1, a2`) and a repeated id is listed once; both are normalised before the summary and the per-agent lines are computed. **Never sum the per-round keys into `cost_ite_qa` by hand:** `cost_ite_qa` stays the whole-list figure the command printed. The release cost report reads the per-round keys, lists a round with `tokens_qa_r<N>` but no `cost_ite_qa_r<N>` under Data gaps, and does not read a 0 or non-integer one as a figure. A round number is 1-based with no leading zero: a `cost_ite_qa_r0` or `cost_ite_qa_r01` key is read as no round and listed under Data gaps as malformed.
   ```bash
   # missing=none uncovered=none
   bd update <bead-id> --set-metadata tokens_qa_r<N>=<this_figure> --set-metadata tokens_qa_r<N>_agent=<task-id> --set-metadata tokens_qa=<ctx> \
     --set-metadata cost_agents_qa=<ids> --set-metadata cost_ite_qa=<ite> --set-metadata cost_calls_qa=<calls> \
     --set-metadata cost_note_qa="all transcripts present" \
     --set-metadata cost_ite_qa_r<N>=<this agent's ite=> --set-metadata cost_calls_qa_r<N>=<this agent's calls=> \
     --set-metadata tokens_qa_note="reviewer agent total — pr-review-merge ran step 4 inline, no code-review fork (ugcportal-cr2h)"
   # INCOMPLETE: no cost_ite_qa / cost_calls_qa total, any old ones removed, the side marked incomplete; per-round keys are not touched
   bd update <bead-id> --set-metadata tokens_qa_r<N>=<this_figure> --set-metadata tokens_qa_r<N>_agent=<task-id> --set-metadata tokens_qa=<per_rule_above> \
     --set-metadata cost_agents_qa=<ids> --set-metadata cost_note_qa="<the note the output names>" --set-metadata cost_coverage_qa="<the marker the output names>" --unset-metadata cost_ite_qa --unset-metadata cost_calls_qa
   # ...and, on INCOMPLETE with missing=none and an ite= on this run's agent line, round N's own keys as well
   bd update <bead-id> --set-metadata cost_ite_qa_r<N>=<this agent's ite=> --set-metadata cost_calls_qa_r<N>=<this agent's calls=>
   ```
   This read-then-write isn't atomic — `bd` has no compare-and-swap for metadata fields (only `--if-assignee`/`--if-status` guard status/assignee changes). If you have reason to think another review pass on the *same bead* is landing its own `tokens_qa` update around the same time, re-read with `bd show <bead-id>` immediately before writing and re-apply the rule above to whatever is there then; otherwise treat the accumulated total as a best-effort approximation, not an exact ledger.
4. **Read the write back before reporting it as made** (`review-standards` section 6, mitigation 3):
   ```bash
   node scripts/bd-verify-metadata.mjs <bead-id> tokens_qa=<value_written> cost_ite_qa=<ite> cost_calls_qa=<calls> cost_ite_qa_r<N>=<agent ite> cost_calls_qa_r<N>=<agent calls>   # on INCOMPLETE: cost_coverage_qa=<marker> in place of cost_ite_qa/cost_calls_qa (keep the cost_ite_qa_r<N>/cost_calls_qa_r<N> pair when you wrote it), and check the printed keyset has no cost_ite_qa / cost_calls_qa total while every per-round key recorded before is still there
   ```
   `bd update` exiting 0 is not evidence the value landed: a mistyped key writes a real key and exits 0, leaving `tokens_qa` holding the *old* figure while the orchestrator records it as updated — and because `tokens_qa` accumulates across rounds, the next round adds its own figure to a number that silently never moved. The verifier prints the bead's whole metadata keyset, so a typo'd sibling key is visible beside the one that should have changed. A non-zero exit means do not report the figure as recorded; name the bead and the exit code instead.

   This matters more here than anywhere else in this file, because nothing downstream ever cross-checks `tokens_qa` against another source. `cut-release`'s Cost Summary reads these fields and nothing else, so a write that silently did not land does not show up as an error — it shows up as a smaller, confident number in a release note.

5. **Record the round's findings by family and severity (ugcportal-2jvh).** The **orchestrator** writes `findings_r<N>` from the reviewer's report once the run has finished. **`N` is the round-marker number the run stamped on the PR** (the `<!-- ugcportal-review-round: N -->` of step 4b), not the bead's own count of review runs: the report reads `findings_r<N>` against marker `N`. A run that stamped no marker (a run whose step 1a lock write was denied by permissions and that reviewed anyway on its orchestrator's instruction, as on #281, whose recorded reason on `ugcportal-nr72` is "round 1 posted no marker: lock write denied; findings taken from the reviewer's report"; a run that lost the step 1a lock race stood down and reviewed nothing, so it has no findings to record) records its findings under `findings_unstamped`, never under a numbered key; with more than one such run the value is the runs' strings comma-joined. The reader lists those under Data gaps as "unstamped review passes" and does not match them to a marker. The reason is that one writer owns the bead's QA record (the same writer as `tokens_qa`), so the two cannot disagree about which round they describe; it is not that the reviewer run could not write, since step 5a has it run `bd create`. The report must therefore list every finding with the family (step 4.1) and the severity the reviewer assigned it (step 6 asks for both). Value format, one string per round:
   ```
   findings_r<N>="f1:<n> f2:<n> f3:<n> f4:<n> med:<n> low:<n>"
   ```
   - `f1`-`f4`: how many findings the reviewer put under each of the four recurring families of step 4.1, counted from the family label on each finding. If a finding's label and the report's "Families" list disagree, the label on the finding wins, and a list entry that is not a numbered finding does not count. A finding the reviewer names under two families counts in **both**, so `f1+f2+f3+f4` can exceed the number of findings; `med` and `low` count each finding once.
   - `med`: findings of medium severity or above. `low`: findings the reviewer called low. A finding with a stated severity counts under `med` or `low` accordingly. A finding with no stated severity goes only under ` unstated:<n>` (the field is omitted when `n` is 0), never under `med` or `low`; the release cost report counts `unstated` findings as medium-or-above, as step 4 does for an unclassified finding.
   - A clean round is `f1:0 f2:0 f3:0 f4:0 med:0 low:0`. Do not record a round that blocked on findings as all zeros: when the verdict prose states findings (labelled severities, or a bare count such as "three findings" that is not a back-reference like "round-2 findings") and the key is all zeros, `scripts/release-cost-report.mjs` reports the round as inconsistent and keeps the prose figure (pinned by the guardrail test in `scripts/release-cost-report.test.mjs`). A bare count does not do this only when the verdict line itself (the first non-empty line of the comment after the marker lines) is approval-shaped: it opens with "Approved", "Auto-approved", "Clean", "No findings", "Zero findings" or "Verified clean", contains one of the report's no-findings phrases ("no findings", "no blocking findings", ...), states no findings count ("3 findings"), and contains none of "Blocking:", "Not merged", "block"/"blocks", "left for a human". Only that line is read (an addendum comment's bare count still joins the round and clears this, 4hsc), so the rule has these consequences:
   - A round written in the blocking template ("Review round N (chain ...). **Blocking ...**", including a zero-finding round on a sensitive-path PR) opens with "Review round", so it does not read clean: a bare count anywhere in its prose (a tool's own output such as "claims-audit --pr 285: 12 findings, all hold") makes an all-zero key on it inconsistent, and the report prints a Data-gaps line for it. The figure depends on where the round says it found nothing: when it does so in a body sentence of the form "no/zero [blocking|code] findings" that is not a sub-heading, a tool-output line or inside double quotes ("Review (six finder angles): zero findings.", "Zero findings this round."), the prose reading is stated with zero mediums and zero lows, so the round is a measured zero and only the Data-gaps line is the price of that template; when its only no-findings phrase is a sub-heading ("Verified, no finding:", a line ending with a colon), a tool-output line, a quoted phrase, or, off the first line, one of the weaker phrases ("Nothing to fix.", "The diff is clean.", "found nothing", "none stands as a defect", "no medium ... found"), the prose reading is unstated, so the round prints `r<N>:?` instead of a zero.
   - A verdict line that opens with a qualified no-findings phrase does read clean even while it blocks ("No findings above low; merge requires zero findings, so L1 must be fixed first."), so a later bare count in the body ("One finding, L1") does not flag an all-zero key. The reader cannot catch that shape; keep the key in step with the body by hand.
   - "no blocking findings" on a round 2-6 approval means no *blocking* findings, not that the round found nothing: lows may have been deferred to beads and are then mentioned only by bare count in the body, which the reader does not check against the key. Record those lows as `low:<n>`, not as zeros.
   - A verdict line that quotes the band rule ("merge requires zero findings") after a first word that is not an approval word, or a "Verified, no finding:" sub-heading inside a blocking round, does not read clean (#157 r3, #207 r2, #209 r4; #277 r1, #258 r1). Labelled severities still count.
   - Example: a round with two family-1 lows and one family-3 medium is `findings_r2="f1:2 f2:0 f3:1 f4:0 med:1 low:2"`.
   - **A round that ended by the gate with lows filed appends ` merged:lows-filed`** (ugcportal-kwxh; the tag keeps its name, but it means ended by the gate, not that a merge happened): the round merged, or on a sensitive path ended with the `needs-human-merge` label after reviewing clean under the gate (the merge click is the human's, so every `.claude/skills` PR ends this way); its key reads `med:0` with no `unstated` field and at least one low, and every one of those lows was filed as a bead under step 5a. A round whose lows were all fixed inline under `review-standards` section 3 carries their counts and **no tag**: none was standing and none was filed, and the round is clean for the gate on its own terms. The two readers do not share that view yet: the report reads it as a lows-only round, and `scripts/check-pass-budget.mjs` reads it as **not clean** (`findings_r1="f1:1 f2:0 f3:0 f4:0 med:0 low:1"` selects as clean=false), so at 3 or more passes the bead reads STOP. A distinct reading in both is the open follow-up `ugcportal-t3vj` (discovered from kwxh), not part of the tag. Example: `findings_r2="f1:1 f2:0 f3:0 f4:0 med:0 low:1 merged:lows-filed"`. `scripts/check-pass-budget.mjs` counts a round carrying the tag as clean for the pass budget, as it counts an all-zero one, and `scripts/release-cost-report.mjs` parses it (`parseFindingsKey`, which reads the tag as `mergedLowsFiled`) without listing it as malformed, and marks it as ended by the gate: `#<pr> r<N> ended by the gate, lows filed` beside the lows-only tail count in the five-most-expensive-beads table, and `mergedLowsFiled` on the bead row and in `roundDetail` of the `--json` export. Both normalise whitespace the same way, so a value the budget reads as a gate-ended lows-filed round is exactly a value the report parses with `mergedLowsFiled`. The tag is a suffix on the existing key rather than a separate key such as `merged_r<N>`, so the round's counts and its outcome are one write by one writer and cannot disagree, and the budget can check `med:0` on the same value it reads the tag from. A round that blocked never carries it; on a value with a medium, an `unstated` field or no low the budget reads the tag as not clean and the report lists the value as malformed.
   ```bash
   bd update <bead-id> --set-metadata findings_r<N>="f1:<n> f2:<n> f3:<n> f4:<n> med:<n> low:<n>"
   node scripts/bd-verify-metadata.mjs <bead-id> findings_r<N>="f1:<n> f2:<n> f3:<n> f4:<n> med:<n> low:<n>"
   ```
   - A bead with one reviewed PR uses `findings_r<N>`. A bead with a second reviewed PR (a `feat` PR and a later `fix` PR) uses `findings_pr<number>_r<N>` for every PR, so a later PR's round 1 does not overwrite the first PR's. **When a bead gains its second reviewed PR, the orchestrator first renames the first PR's bare `findings_r<N>` keys to `findings_pr<first>_r<N>` (set the new key, read it back with `bd-verify-metadata`, then unset the bare one), and only then records the second PR's keys.** The reader looks for the PR-specific key first and ignores a bare `findings_r<N>` on a bead with more than one reviewed PR (listed as `multi-pr`, once per key), so an un-renamed first PR falls back to prose. A key for a round the chain does not have is listed as `no-such-round`.

   Only the PR-title bead receives findings keys (item 2); two beads on one PR both carrying keys that disagree is a recording error, listed under Data gaps as `keyed-conflict` with both bead ids (the larger medium count is used for the figure).

   Timing: write `findings_r<N>` once the round's report is in, whether or not the round has a `tokens_qa_r<N>` figure. It does not depend on the token-cost conditions of item 1: findings are recorded whenever the round reached step 4, measurable subagent or not. A round that reached step 4 without stamping a marker goes under `findings_unstamped`, above. A bead with no `findings_rN` keys is still read from the verdict prose by the release cost report, which says how many rounds fell back to that.

**The reviewer run itself never calls `bd update --set-metadata tokens_qa`, `tokens_qa_note` or any `cost_*_qa` key.** It cannot see its own final token total before it has finished running, and guessing one here would be exactly the duration-based estimate this step has always forbidden. This applies regardless of whether the PR ends up merged or left for a human — the QA cost was incurred either way, and recording it is the invoking orchestrator's job once the total is known, not this run's.
