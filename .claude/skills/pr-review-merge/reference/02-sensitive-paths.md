If the changed files (`gh pr view --json files`) touch any of the following, this PR **always** goes to a human — regardless of how clean the diff looks:

*[Text kept verbatim in SKILL.md stood here.]*

- **Anything under `.claude/skills/`** — the review policy itself, and a path with no deny rule and no CI guard covering it (the same is true of `.claude/agents/` below). `.claude/settings*.json` are deny-listed for agents, and the `Fail if .claude/settings*.json or CLAUDE.md is bundled with other changes` step of the `guards` job in `.github/workflows/ci.yml` (which runs `scripts/check-sensitive-files.mjs`) fails any PR that bundles them (or `CLAUDE.md`) with other changes; `.claude/skills/**` is in neither. Yet this file *is* the severity gate, the round cap and the marker-chain integrity checks. Without this entry, a PR that deletes the gate, removes the integrity checks, or simply adds "always merge" here would be eligible for auto-approve-and-squash-merge by the very skill it disarms, with no human in the loop and no CI job to catch it. That is the same self-modification failure `CLAUDE.md` records for `.claude/settings.json` — a work branch editing its own permissions, nearly merged unreviewed — except that one got a gate afterwards and this one had not. "This PR should go to a human because it changes the review rules" must be a mechanism, not a sentence someone remembers to write in the description.
- **Anything under `.claude/agents/`** — each file there is a subagent's system prompt. Weakening its worktree rules, loosening its review obligations, or dropping the reviewer tier to a cheaper model changes every future run of that agent, and the PR doing it would otherwise be eligible for auto-approve-and-squash-merge by the very agents it configures. No edit-deny rule backs this entry: `permissions.deny` in `.claude/settings.json` covers only the two settings files, and the CI step named above does not match this path either, so this step is what routes it to a human.
- **`CLAUDE.md`** — the CI step named above fails a PR only when it *bundles* a `CLAUDE.md` change with other changes; it passes a PR that changes `CLAUDE.md` alone (`checkSensitiveFiles` returns ok when nothing else changed), and no deny rule covers `CLAUDE.md`. So for a `CLAUDE.md`-only PR this step is what routes it to a human, exactly as for `.claude/skills/` and `.claude/agents/`; for a bundled change CI also fails it, and the human routing still applies.

This list is the authority for what routes to a human. `scripts/check-human-merge-labels.mjs` (`SENSITIVE_PATH_RES`, used by `isSensitivePath`) mirrors it in code to classify labels after the fact (it routes nothing) and `scripts/check-sensitive-files.mjs` only points here; when this list changes, change the mirror and its test rows in the same PR, and classify the new entry in `scripts/reviewer-model.mjs` (`GUARD_PATHS`, or `PROCESS_PROSE` with its reason), whose test fails on a step-2 regex it does not classify.

If any of these are touched, still run the review (step 4) and post it as a normal comment, but explicitly state in the comment that this PR requires human approval/merge because it touches a sensitive path, and do not call `gh pr review --approve` or `gh pr merge`.

**Mark the PR as waiting on a human (ugcportal-ub7y).** A comment alone leaves the PR findable only in chat. The label `needs-human-merge` means exactly one thing: **the latest round reviewed clean, and a human must merge because the PR touches a sensitive path**. It is applied only at that stop (the removal rule is below). A stop with a blocker, including the round-6 escalation (step 5, row 6: "a blocker here ends in escalation"), is not reviewed clean and gets no label. Two other zero-finding stops are **not labelled for their chain state**: an `approx` chain that reaches the "treat as 6" fallback (a run at round 7+ that fails condition 1 or 2 of step 5's `7+` row (the entry conditions, which step 5b points back to) stamps the non-counting `approx-cap` stop, step 5) and a `broken` chain (the non-counting `chain-broken` stop). Those two stamp no round comment, so the verdict marker has no round comment to sit in and `scripts/check-human-merge-labels.mjs`, which starts from the round marker, would read a correct label there as stale. They are tracked in ugcportal-osth; until it ships, those stops are findable only in chat. An `approx` chain that reaches round 6 *by counting* is not one of them: it stamps a counting `6` or `6 approx` marker like any round (step 5, step 5b), so its zero-finding stop is a round comment and is labelled under the sensitive-path rule below. **Precedence:** when a sensitive-path PR is also at one of the two non-counting stops, the sensitive-path stop governs: if the run reviewed clean, label it and put the verdict marker in the stop comment (the check does not read the stop comment, it reads the latest round comment, so it lists that label as C when that round comment lacks the verdict marker, as when the stop follows a blocked round, or when the PR has no round comment by the reviewer at all, as when a `chain-broken` stop followed markers from another account, which the check ignores; after a labelled clean round it lists nothing on the same head and D if the head moved; ugcportal-osth tracks reading stop comments); if it did not review clean, no label. When the round applied an inline fix (`review-standards` section 3), the label goes on only after step 5's "After an inline fix" checks have passed: for a fix commit, CI on `<fix-sha>` reads PASS on every row and the round comment carries `inline-fix head=<fix-sha>`; for a body or title edit, the Guards run the edit started reads PASS.

The reviewer run applies and removes this GitHub label. The bead label `stalled-on-human` is set by the **orchestrator**, not the reviewer run: the orchestrator owns the bead's lifecycle labels, so one writer sets and clears them, and step 6 carries the instruction. **Orchestrator briefing rule: an implementer brief never tells the implementer to apply `needs-human-merge` at open, and the implementer never pre-labels.** A label before any review would show the human "reviewed clean, merge me" for a PR nobody has reviewed; this sentence is in this skill only, so the orchestrator carries it into every implementer brief (`worker-implementer.md` needs the same line, which is outside this change). **Who removes the labels, and when (the one rule; step 5, step 6 and `worker-reviewer.md` point here).** The reviewer applies the GitHub label at a sensitive-path reviewed-clean stop and removes it (`gh pr edit <n> --remove-label needs-human-merge`, and asks the orchestrator to remove `stalled-on-human`) when a later round has a blocking *finding*; the sensitive-path gate itself never removes it. A label left on a blocked PR shows the human "reviewed clean, merge me" in the dashboard's Merge needed list. A push after a labelled clean round makes the label stale: it sits on commits no round reviewed, and the check lists it as D. The next round then removes it (blocking findings) or re-applies it with a fresh verdict marker (reviewed clean). The orchestrator removes both labels when it closes the bead after the PR has merged (step 6).
