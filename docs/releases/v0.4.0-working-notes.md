## The short version

This release was planned as Instagram-sourced UGC resale. It ends with the Instagram integration
deferred and **manual image and video upload as the product**.

Nothing failed to make that happen. Two deliberate decisions did, one after the other:

1. **`2eh` — Meta's Platform Terms make API-fetched media unsellable.** §3.a.iv prohibits selling
   Platform Data and §12 defines that as anything obtained through the API. Option A was chosen:
   the API is for *discovery only*, and the sellable asset is the owner-uploaded original. That
   already made uploads the centre of the product.
2. **Instagram deferred entirely.** With the API reduced to discovery, its remaining value did not
   justify the OAuth, token-refresh, deauthorize-callback and sync work in front of it. Six beads
   were deferred with their specs intact rather than closed.

The consequence worth stating plainly: **several things in this release were built against a model
that is no longer the product's centre.** They still work, and the re-anchoring was done rather
than merely tracked: `vsm` moved `ResaleRightsReview` onto the uploader, so it is anchored on
`uploaderUserId` and no longer references `InstagramAccount` at all. What survives the move is the
*shape* of the questions — the resale-rights checklist still asks about a connected account,
because it was written for one. That mismatch is what `9cs` is about, and it is why an uploader
with no Instagram account cannot currently be cleared under `2026-09-27.1`.

### Decisions taken by implementing agents, worth noticing

These were judgement calls that went beyond the instruction, and in each case the agent's reasoning
was better than the instruction it was given.

- **`e86` refused to add a deadline on admitted tasks.** A libvips call cannot be cancelled, so a
  deadline would abandon the promise while the operation kept its memory and hand the slot to a new
  caller — causing exactly the overshoot the gate exists to prevent. It narrowed the claim instead
  and added `longestRunningMs` so a wedged slot is detectable.
- **`e86` documented a 1 GB floor rather than tuning defaults to fit 512 MB.** The arithmetic did
  not fit; massaging the defaults would have produced a configuration the container could not honour.
- **`r1d` refused to record a limitation it had disproved.** Told (by me, relaying a review) that
  Prisma cannot express a sqlite partial index, it verified that 7.10 can behind a preview feature,
  measured the benefit at ~46x, and declined to write the false claim.
- **`r1d` chose an opaque indirection over reshaping the storage key.** A new key format only
  protects rows uploaded after the change; every existing row would have kept leaking.
- **`0ss` used the SYSTEM path, not ADMIN, when disconnect revokes a clearance.** The ADMIN branch
  stamps `reviewedByUserId`, and recording the disconnecting admin as the *reviewer* would forge a
  review that never happened.
- **`0ss` reversed its own earlier decision** to refuse requests with no `Origin` header: no browser
  omits it cross-origin, so absence cannot be an attacker's form, while some legitimate clients omit
  it. Its own summary — "that refusal was an outage dressed as a defence".

### What `n3c` turned into that the bead did not ask for

The bead asked for an upload form. What it needed, and what took three review rounds to arrive at,
was a client that does not lie about outcomes it cannot observe.

The first implementation reported a cancelled or timed-out upload as "cancelled" and offered a
retry. Review pointed out that this is a claim the client is not in a position to make: once the
last byte of the body has gone out, the client cannot know whether the server stored the file. A
retry then risks a silent duplicate, because `POST /api/media` has no idempotency key.

The fix was to make the transport record whether the body was fully delivered, and split the
failure vocabulary on that fact:

- **Before delivery** — the request was cut off mid-stream, the route's multipart read fails,
  nothing is stored. Confident message, retry offered.
- **After delivery** — cancel, network drop and stall all collapse to one `outcome_unknown`:
  *may or may not have been stored; check your library before uploading it again.* Retry
  withheld, not because a retry could not work, but because this client cannot offer one without
  risking a duplicate.

The same round replaced a 120-second watchdog — a guessed number that was the sole bound on the
server's post-body work — with a bound re-anchored to the server's own 300s `requestTimeout`,
past which there is genuinely nothing left to wait for.

The server-side half is filed as `2u9`: honour `request.signal`, and accept an idempotency key.
Its description records that closing it should also re-enable this page's retry, so the mitigation
does not outlive the defect it works around.

### Two assertion bugs the agent caught in its own tests

Worth recording because they are the same species, and because it is the species the fixture-
mutation habit exists to catch — an assertion that compares the wrong two things and therefore
cannot fail:

1. `toContain("disabled")` passes in **both** directions. Every Button in this codebase ships
   `disabled:pointer-events-none disabled:opacity-50` in its class list, so the needle is present
   whatever the button's state, and the assertion proves nothing about whether it is disabled.
   (Worth recording that the agent's own summary stated this backwards — it wrote "`not.`
   toContain" — while the code comment it committed at `upload-flow.test.tsx:596` states it
   correctly. The backwards version was then repeated downstream three times before a later
   reviewer checked `git log -S` and established that the negated form has never existed in this
   repo. A defect description is itself a claim, and this one travelled further than the defect.)
2. React escapes the apostrophe in `server's` to `&#x27;`, so matching the prose as written
   compared the markup against a string it could never contain.

Neither would have been caught by "do the tests pass?". Both were caught by asking what weaker
implementation would still pass.

### `71y` and the race that kept moving

Three rounds, and the agent's own summary of the pattern is the most useful sentence in the whole
release: *"twice now I described a fix as closing a race it had only moved. Both times the error

The concrete case: `loadAndOpen`'s `if (window.pswp) return false` does not serialise two opens at

### The thing no review could have found

While auditing the gallery-chain beads' premises before handing them to agents, a question surfaced
that no bead had ever owned: **who is allowed to have an account?**

`src/lib/auth.ts` has a `callbacks:` block containing only `session`. There is **no `signIn`
callback at all** — the `signIn` at line 54 is in the `events:` block, and Auth.js discards event
return values because events fire after sign-in has already succeeded. So nothing in the
configuration is in a position to refuse anyone. Google and Facebook are both configured. And
`POST /api/media` gates on `session?.user?.id` and nothing else.

That sentence took three attempts to get right, which is the part worth recording. The bead as
originally filed said the `signIn` *callback* "returns nothing, which allows the sign-in" — right
conclusion, invented mechanism, and an implementer following it would have added `return false` to
an event handler and shipped a change that compiles, typechecks, runs and refuses nobody. A review
of an unrelated PR caught it. The correction issued to the implementing agent then carried its own
error, repeating "a non-`false` return allows the sign-in" as though that were the rule. The agent
checked `node_modules` rather than taking either of us at our word and found the truth: in
`@auth/core` — which resolves to `0.41.3` here; the `beta.32` in `package.json` is the `next-auth`
range, and conflating the two is its own small instance of the family this section is about —
`defaultCallbacks.signIn()` returns `true` and `handleAuthorized` throws
`AccessDenied` on any **falsy** return, while a *string* return is read as a redirect URL. The open
door was the missing callback and nothing else.

Three claims about one file, each written with a line number attached, each wrong in a different
way, and all three read as verified precisely *because* they named a file and a line. The thing
that actually settled it was reading the installed dependency. This is the same defect family the
release spent six review rounds learning to sweep for — and it was the orchestrator writing it into
a P0 bead, not an agent writing it into a comment.

So the authorisation model, as actually built, is: anyone on the internet with a Google or Facebook
account can sign in, upload arbitrary images and video into the object store, and publish them to
the public gallery — publishing requires only ownership of the row, which the uploader has by
construction.

Every one of those gates is correct. Every one was reviewed and found correct. The defect is that
"authenticated" was allowed to stand in for "authorised" across three separate beads — `8wa` (the
upload API), `n3c` (the upload UI) and `r1d` (publish) — and each of them was right to assume the
question had been settled somewhere else. It had not been settled anywhere.

This is worth dwelling on, because it is the counter-example to everything else in this document.
The release's expensive lesson so far has been *review harder* — sweep for defect families, mutate
the fixtures, check what span a guard covers. None of that would have found this. It is invisible
in any single diff, because no single diff is wrong. What found it was auditing a bead's
**premises against the running code** before starting work, which is a different activity from
reviewing a diff and costs a fraction as much.

Filed as `egp`, P0, labelled `release-decision`. It compounds `3ae` (publishing is ungated by the
rights review, so a stranger can put a recognisable person on a public gallery operated from
Norway) and `321` (nothing has ever run against live storage, so the first real deploy would also
be the first exposure). It is not urgent today only because nothing is deployed.

### What the premise audit cost and returned

Auditing the five gallery-chain beads before starting them took one pass and turned up, besides
`egp`: `lju` has no item page to share a link to (`src/app` has four routes and none of them is an
item); `9sz` assumes a `featured` flag that does not exist anywhere in the schema; `137` assumes a
many-creator marketplace, which the single-seller checkout in `p3v` contradicts; and `lb8`'s
"authenticated user" is a set defined entirely by the `egp` accident.

Four of five beads rested on a premise that had quietly stopped being true. Each would have been
discovered by an agent somewhere in round two or three, as scope it had to invent. That is the
mechanism behind `ws3`'s question — *why do some beads take ten rounds?* — and at least part of the
answer is that the rounds were spent rediscovering that the bead was wrong, not that the code was.

### One memory that paid for itself

`bd remember` holds a note saying that a worktree without `npx prisma generate` silently fails to
*collect* test files, so the run reports a plausible-looking lower total rather than erroring — and
that the symptom to watch is the collected **file** count dropping without a test being deleted.
It was written after four wrong test counts were quoted in a single session.

It fired for real while `egp` was being built. That agent rebased onto a `main` that had just
picked up `photoswipe` and `jsdom`, and its first post-rebase run reported 1255 tests with two
files failing to collect. It recognised the symptom by name, ran `npm ci`, and got the true figure
— 65 files / 1585 tests, matching CI exactly.

Worth recording because the cost asymmetry is the whole argument for writing these down. The note
took two minutes. Without it, the agent's options were to report 1255 as a real number (which is
what happened the four previous times) or to spend a round discovering the cause from scratch.

## What building it taught us

Two defect families accounted for most of the review effort across this release, and both are now
written into the `bead-template` skill:

**A comment claiming a guarantee the code does not make.** A guard reading `previewKey !== null`
after that column left the projection, so it evaluated `undefined !== null` and passed everything.
A type constraint that blocked bad values going in but not coming out, because `keyof` an
optional-`never` property still yields the key. A documented memory figure that priced one code
path of four.

**A check comparing the wrong two things.** A request-derived origin compared against
configuration. Two columns written by the same author, which proves self-consistency and not
ownership. And the NaN variant — `NaN <= number` is `false`, so an unreadable expiry date skipped
the expiry check entirely and the rights gate returned *sellable*.

`0ss` alone had **six fail-opens** found across its rounds, four of them the same family, several
introduced by the fix for the previous one. What it leaves behind are structural tests that read
their subject out of rendered markup rather than a hand-written list, so a field added later is
covered the day it exists.

The process response is `2yj`: a severity-gated stopping rule, a six-round cap, a scope freeze after
first push, and a pre-flight sweep for those two families.

cannot be handed to an agent. It is the single largest piece of unverified surface in v0.4.0, and
it is worth being blunt that a green CI run on this release does not mean a photograph has ever
made it from a file picker to a gallery tile.

## Cost

Measured from bead metadata, for the five largest beads only:

| | tokens |
|---|---|
| Implementation | 3.40M |
| Review | 1.32M |
| **Combined** | **4.73M**, averaging ~0.95M per bead |

Two corrections to the premise these came from. `ugcportal-2yj` says "nine implementation rounds
and eight review rounds"; counted from the beads' own merge notes the real worst case is **ten
implementation rounds and nine review passes** (`r1d`), with `e86` at 9+8 and `0ss` at 7+7. That
matters for the argument rather than just the arithmetic: against nine rounds a six-round cap is a
genuine constraint rather than a formality. And the token figures themselves are dated 2026-09-25
and have since moved to roughly 3.49M / 1.56M as `tokens_qa` accumulated.

Treat these as an upper bound with a wide error bar. `tokens_impl` sums resumed agent runs that
replay context, so it overstates marginal cost; several `tokens_qa` figures are missing entirely
because those review passes returned without a measurable subagent run. The *ratio between beads*
is the trustworthy part, and it is what motivated `2yj`.
