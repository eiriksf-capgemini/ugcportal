# Release cost: v0.4.0 vs v0.5.0

What each bead in the two latest releases cost to build and to review, how many review rounds its PR took, what the reviewer found per round, how the planned model tier performed, and what to change for v0.6.0. Written for `ugcportal-apsq` on 2026-10-05, the day v0.5.0 was cut. The process changes themselves are `ugcportal-wzgw`'s; this document says which of its proposals the numbers support, and by how much.

Every table in the appendix is regenerated by `node scripts/release-cost-report.mjs` (section 9). The numbers quoted in the prose are copied from that run; if a figure in the prose disagrees with the appendix, the appendix is right and the prose is stale.

## 1. Read this first: what the figures can and cannot say

- **Totals are lower bounds.** `tokens_impl` is recorded on 27 of 38 v0.4.0 beads and 32 of 54 v0.5.0 beads; `tokens_qa` on 16 of 38 and 29 of 54. Of the v0.5.0 feature beads, `3wgp` (cookie consent) and `qnq9.7` (about/portfolio pages) have no build figure at all, and `gwr` (alt text) has no review figure. A bead with no figure costs zero in every total below. It did not cost zero.
- **`~` means the bead's own notes call the figure an estimate.** Several `tokens_impl` values were written as "rough estimate, implemented inline in the orchestration session" (`1551`, `cl4e`, `000`, `5g9t`, `juo`, `e5zf`, `r3h`, `7z48`, ...). The script marks them from the words *estimate*, *rough* or *approx* in a sentence that also names a token figure, so the mark is mechanical, not a judgement. An unmarked figure is one whose notes make no such claim, which is not the same as a measured one.
- **`tokens_qa` accumulates across rounds.** It is one number per bead, summed by `pr-review-merge` from each review fork that reported usage. **Per-round review cost is not recorded anywhere.** Where this document splits review cost into "first round" and "tail", it divides `tokens_qa` by the round count and multiplies by the number of rounds in each part. That is a crude mean, labelled as such everywhere it appears, and it almost certainly overstates the tail: later rounds verify a smaller delta than round 1 reviewed. The sibling investigation (`ugcportal-wzgw`) wants per-round figures; section 8 says how to record them so the next report does not have to guess.
- **Model tier is the planned tier, not the model that ran.** `metadata.model` is what the bead's author thought the work needed. Which model actually executed each agent run lives only in the orchestration transcripts. `.claude/skills/harness-cost-controls/SKILL.md` section 6 (`ugcportal-bf7`) measured the consequence: until `ugcportal-2tc` set `CLAUDE_CODE_SUBAGENT_MODEL=sonnet` globally on 2026-09-29, a `sonnet`-tagged worker spawn without an explicit `model` argument inherited the parent's Opus, so **most "sonnet" beads in v0.4.0 plausibly ran on Opus, and the sonnet/opus comparison for that release is not a comparison of models.** The same section says, and this document repeats: **do not recalibrate `CLAUDE.md`'s model-fit table from these figures.** v0.5.0 (2026-09-29 to 2026-10-05) is the first window with the fix in effect and is therefore the first window where the tag means something, but it is one week, 21 sonnet beads with a round count, 6 opus, 7 haiku. Section 5's routing table is a proposal to test against v0.6.0, with the per-bead and per-round figures as the calibration signal; it is not a measured result.
- **Mediums per round are the severities the reviewer stated**, read from the verdict comment that carries each round marker (`MEDIUM`, `**medium**`, `[Medium]`, `LOW:` and so on), with addenda folded into the round they name. Where a verdict states no severity (the implementer fix reports on `#43` rounds 1-4, `#61` rounds 1-3, `#51`), the table says `?` rather than inferring one from the finding's content. Lows are reported as a **label count**: one `LOW:` label routinely introduces several semicolon-separated items, so the lows column is a floor, not a count of findings.
- **v0.4.0 PRs predate round markers** (the stopping rule landed with `#43` on 2026-09-28). Their round counts come from each bead's close reason ("seven review passes"), marked `(cr)`, and their findings were inline review comments, 341 of 410 of which carry no severity label. For those PRs the "mediums by round" column reports the labelled count, the unlabelled count, and the number of time-clustered comment bursts (`~`), which is an estimate of rounds the script deliberately does not use as one.
- **Release membership is the CHANGELOG section**, cross-checked against the git tag range, not `metadata.release` (set on 16 of the 54 v0.5.0 beads). `git log v0.3.0..v0.4.0` returns only six commits because the two tags share no merge base (v0.4.0 sits on a re-rooted six-commit history), so for v0.4.0 the cross-check falls back to PRs merged between the tag dates. `git log v0.4.0..v0.5.0` is 52 commits and reconciles with the CHANGELOG except where section 7 says.

## 2. Headline findings

| | v0.4.0 (2026-09-18 to 09-28) | v0.5.0 (09-29 to 10-05) |
|---|---:|---:|
| Beads shipped | 38 | 54 |
| Recorded build cost (`tokens_impl`, lower bound) | 16.6M (27 beads) | 11.1M (32 beads) |
| Recorded review cost (`tokens_qa`, lower bound) | 5.0M (16 beads) | 19.4M (29 beads) |
| Recorded total (lower bound) | 21.6M | 30.5M |
| Review share of recorded cost | 23% | 64% |
| Median build cost per bead with a figure | 523,716 | 199,917 |
| Median review cost per bead with a figure | 316,261 | 524,812 |
| Median review rounds per bead with a count | 5 (n=19) | 5 (n=38) |
| Beads whose PR reached the six-round cap | 5 | 12 |
| Mediums the reviewer stated, marker PRs, each PR once | 2 (only `#43` had markers) | 84 across 35 PRs |

1. **The money moved from building to reviewing.** Recorded build cost fell by a third while recorded review cost quadrupled; review went from under a quarter of the recorded total to nearly two thirds. Part of that is better recording (29 beads with `tokens_qa` against 16), but the per-bead medians move the same way: the median bead got 2.6× cheaper to build and 1.7× more expensive to review.
2. **Rounds did not fall; the cap got busier.** The median PR still takes five rounds. Twelve v0.5.0 beads hit the cap against five in v0.4.0, and every one of the twelve went to Eirik for a manual merge because the reviewer runs under the PR author's account, which makes every chain `approx` and the lenient round-4-5 row unreachable (`pr-review-merge` step 4b, `review-standards` section 3).
3. **Rounds 5 and 6 earned almost nothing.** Across the 35 v0.5.0 PRs with markers, 129 rounds ran: 50 found at least one stated medium, 58 found only lows, 17 found nothing (and 4 state no severity). By round number: rounds 1-4 found a medium in 46 of 99 rounds (46%); **rounds 5-6 found a medium in 4 of 30 (13%)**. The crude tail estimate (`tokens_qa / rounds × lows-only tail rounds`) is ~7.0M of the 18.7M recorded review tokens, 38%, spent on rounds after the last medium. That is the identity change's price tag, and it is the single largest line in this report.
4. **Features cost ~2M tokens each and all but one hit the cap.** The ten v0.5.0 features recorded 5.2M build and 9.9M review; median build 715k, median review 1.23M, median six rounds, five of ten at the cap. The three sonnet design features (`14k9` header, `akv6` footer, `6dvg` front page) cost 2.1-2.2M each, and in each the reviewer stated one medium per round for rounds 1-3 and lows only after that.
5. **Fixes are the second bill, and one "small" fix cost more than any feature.** Eighteen fixes recorded 4.4M build and 7.2M review. `jx4` (keyboard focus through Load more) recorded 2.0M build as the exact subagent total across six implementation passes, plus 498k review over six rounds, four of them lows-only. `1b2c` (503 on unreachable storage) recorded 1.84M review with no build figure.
6. **Opus found the mediums that mattered and still hit the cap.** The six opus beads with a round count stated 27 mediums (`rw9j` 12, `t33p` 6, `ysub` 6, `mzr` 2) and none passed in two rounds; three of six reached the cap. The v0.5.0 close reason's "eleven mediums" for `t33p` + `ysub` is right once `t33p`'s round-6 outstanding medium (filed as `qqgi`, not fixed) is set aside: 11 fixed, 1 filed.
7. **Haiku passes fast on mechanical work and loses on anything with a test.** Four of seven haiku beads passed in one or two rounds (`4at`, `asg`, `e5zf`, `r3h`); `o7l` (`/llms.txt`) took five rounds and five mediums, two of them vacuous tests, and its review (769k) cost 2.4× its build (316k). Its own close reason draws the line: "haiku implementer; the two vacuous-test rounds argue for sonnet on anything with a guardrail test."
8. **The planned tier did not move the round count.** Sonnet, opus and fable beads with a round count all sit at a median of five or six rounds in v0.5.0. What differs is what the rounds found: opus rounds found mediums (27 in 30 rounds), sonnet rounds found lows (51 mediums in 94 rounds, ~450 low labels). The round count is set by the process, not the tier, which is why section 6 spends more words on the process than on routing.

## 3. Where the review tokens go

Round economics for the 35 v0.5.0 PRs with round markers (each PR once; `#101` is shared by `ig4g` and `52ue`, `#60` by `5dr6`/`plp6`/`ws3`):

| Round | Rounds run | Found ≥1 medium | Lows only | Nothing found | Severity unstated |
|---|---:|---:|---:|---:|---:|
| 1 | 35 | 15 | 8 | 10 | 2 |
| 2 | 23 | 11 | 9 | 2 | 1 |
| 3 | 21 | 10 | 8 | 2 | 1 |
| 4 | 20 | 10 | 10 | 0 | 0 |
| 5 | 18 | 2 | 14 | 2 | 0 |
| 6 | 12 | 2 | 9 | 1 | 0 |
| **All** | **129** | **50** | **58** | **17** | **4** |

Three things follow.

- **Round 1 blocks 25 of 35 PRs** (15 with a medium, 8 with lows, 2 unstated). Ten PRs were clean at round 1, all small: `4at`, `5g9t`, `ggw`, `qnq9.14`, `asg`, `000`, `cl4e`, `e5zf`, `lykb`, `r3h`'s second PR. Nothing feature-sized has ever passed round 1 in this repo. That is the pre-review target (`wzgw` item 2): the first round is paid for by a fresh reviewer at full depth, and it is currently finding things a sweep on the branch could have found.
- **Round 4 is the last round that reliably earns.** Half of round-4 runs found a medium, several of them the re-merge breakages and precondition conflicts of a PR that had sat open while `main` moved (`#94` round 4: "main has moved again with #92"). Rounds 5 and 6 found four mediums between them in 30 runs: `#98` round 6 (the untested P2002 race branch, filed rather than fixed), `#92` round 6 (an extension of a round-4 finding), `#81` round 5 (bootstrap promotion ignoring the provider binding, a real authz medium) and `#79` round 5. Under an `exact` chain, 11 of the 12 cap PRs would have merged at round 4 with their lows filed; the rounds-5-6 mediums on `#81` and `#98` are the residual risk the gate accepts and both are auth code, which argues for keeping auth-scoped beads on the strict rule even after the identity change.
- **The tail is where the family-1 findings live.** The 58 lows-only rounds are dominated by comments that claim more than the code does: `#97` rounds 4-6 are entirely about what an e2e motion spec's comment says it verifies; `#98` rounds 4-5 are doc sentences about the lockout cure; `#101` rounds 2-5 are the scan test's own coverage claims. Each fix round added prose, and each new paragraph was the next round's surface. `wzgw` item 4 (measurements belong in tests, comments point at the test) is the direct answer; the identity change makes it cheaper rather than unnecessary, because a low found at round 4 still costs an implementer pass to fix before the merge.

Crude cost of the tail: for the 33 marker PRs with a `tokens_qa`, `tokens_qa / rounds × tail rounds` sums to **~7.0M of 18.7M (38%)**. Even if a late round costs half of a first round (which it should, since it verifies a delta), that is ~3.5M tokens per release spent on rounds that found no medium.

## 4. Model tier performance

Repeat of the caveat: the tier is the planned one, v0.4.0's sonnet rows largely ran on Opus, and v0.5.0 is one week of data. The harness-level measurement (`usage_indicators.py --project ugcportal`, list-price dollars, notional under a seat) agrees that the routing fix took effect between the two releases: Opus held **~88%** of subagent spend in the v0.4.0 window (09-18 to 09-28: ~$1,318 of ~$1,491) and **~25%** in the v0.5.0 window (09-29 to 10-05: $478 of $1,901, of which 10-05 includes the post-release investigations, so `~`). Sonnet went from ~9% to 66% of subagent spend. So v0.5.0's sonnet beads are, for the first time, mostly sonnet.

Reading it:

- **Haiku** is the only tier whose output passes in one or two rounds more often than not, and every one of those passes was a one-file change with no new test (`4at` comment fix, `asg` one-call refactor, `e5zf` gitignore line, `r3h` banner text). Where haiku wrote a guardrail test it lost: `o7l` five rounds, two vacuous tests; `e15` three rounds (round 1 found a hunk leaked from the orchestrator's checkout, which is not haiku's fault, round 2 found the hunk "reported removed but not", which is). Review cost per haiku bead (median 124k) is five times its build cost (median 25k); the review is not cheaper because the implementer was.
- **Sonnet** carried the release: 21 beads, 8.1M build, 11.6M review, 51 stated mediums. A third passed in two rounds, a third reached the cap, and the cap third is exactly the feature list. The design features each reached five or six rounds with one medium per round for three rounds (`14k9`: invisible toggle, no Escape dismissal, re-merge breakage; `akv6`: contact form encoding, draft guard, footer tagline; `6dvg`: text over opaque decoration, an unguarded session await, a contrast pairing on the wrong token). None of those three mediums per PR needed a stronger model to write; each was found by executing the page, which `wzgw` item 2's pre-review would do before the PR exists.
- **Opus** never passed in two rounds and half its beads hit the cap, but its rounds found mediums at nearly one per round (27 in 30) and they were the release's heaviest: `t33p` (two configured people merged through a shared browser, one-directional link guard, address-collision lockout), `ysub` (TSX parsing of `.ts` generics, an unterminated comment erasing a file, the `require` callee matrix), `rw9j` (twelve contrast regressions across five rounds). The `rw9j` case is the one that says tier is not the lever for correctness: an opus/xhigh implementer shipped twelve measurable contrast regressions because the gate (`findAlphaColorUtilities`) only scanned alpha-modified utilities; round 2 finding 4 named the gate gap, and that gap, not the model, is what let the other eleven ship.
- **Fable** on `qnq9.4` (privacy and licence pages) took six rounds and 31 low labels, almost all about the code guards around the text rather than the text; the one medium (round 3) was a scan over interpolated page text. The judgement half of that bead was done by round 1; the remaining five rounds were a sonnet-shaped job on a fable-priced bead. `qnq9.14` (three wording decisions) was one round at 6k build, which is the shape fable beads should have.

## 5. The five most expensive beads of v0.5.0, and one reduction each

Ranked by recorded total (build + review, lower bound). Cost split: build is `tokens_impl`; "first-round review" and "tail" are the crude `tokens_qa / rounds` mean times one round and times the lows-only tail rounds respectively, so both carry `~`. The reduction named for each is the one that would have cut the most, with the number it rests on.

| # | Bead (PR) | Total | Build | Review (rounds) | Mediums by round | Lows-only tail | ~First-round review | ~Tail review |
|---|---|---:|---:|---:|---|---:|---:|---:|
| 1 | `jx4` Load more keeps keyboard focus (`#87`) | 2.51M | 2,008,736 (exact, six passes) | 498,149 (6) | r1:1 r2:1 | 4 | ~83k | ~332k |
| 2 | `ysub` guard scanner on TypeScript's lexer (`#95`) | 2.30M | 536,035 | 1,764,205 (6) | r1:2 r2:1 r4:3 | 2 | ~294k | ~588k |
| 3 | `14k9` header (`#94`) | 2.20M | 880,124 | 1,316,502 (6) | r1:1 r3:1 r4:1 | 2 | ~219k | ~439k |
| 4 | `akv6` footer (`#96`) | 2.13M | 771,662 | 1,359,898 (5 + post-cap verification) | r1:1 r2:1 r3:1 | 2 | ~272k | ~544k |
| 5 | `6dvg` front page (`#97`) | ~2.07M | 886,369 | ~1,187,182 (6) | r1:2 r2:1 r3:1 | 3 | ~198k | ~594k |

Just outside the five, and relevant because their build cost is missing: `1b2c` (503 on unreachable storage, 1.84M review, six rounds, 22 low labels), `3wgp` (1.75M review, six rounds, ten mediums), `1551` (1.57M review, six rounds, chain `{1,4,5,6}` with rounds 2-3 never stamped).

1. **`jx4`: stop the implementer at three passes.** The build figure is the exact subagent total across six implementation passes, ~335k per pass, for a focus-management fix whose two mediums were both found by round 2 (an invisible programmatic focus target; a focus handoff firing after the visitor had moved). Rounds 3-6 were lows (21 labels) and each cost a fresh implementer pass with a fresh worktree. Reduction: a per-bead stop rule at three implementation passes without a clean round (section 6, budget B2) would have capped this at ~1.0M build and sent the remaining lows to a bead, which is where they went anyway (`dj4i`, seven post-cap lows). Under an `exact` chain the PR merges at round 4; that alone saves the two last passes, ~670k build and ~166k review.
2. **`ysub`: resume the reviewer instead of respawning it.** Six rounds at ~294k each, the highest per-round figure in the release, on a PR whose round-5 and round-6 deltas were "comments and one test title only, zero code change" (round 6's own words). A fresh reviewer re-establishing the fuzzing harness, the 267-file gap walk and the lint-shape matrix each round is what the per-round figure is paying for. Reduction: `wzgw` item 3, one reviewer per PR resumed with the new head; the round-5-6 verification of comment rewrites should cost a fraction of a full pass. If the resumed delta round costs half, that is ~290k on this PR alone. The bead-level reduction is upstream: `3wgp`'s cap escalation handed over a hand-rolled scanner with known bypasses, and the parser swap `ysub` made is the same one `plp6` made two weeks earlier on `#60`; a pre-review item "does this diff hand-roll a tokenizer?" would have routed it to the TypeScript scanner at `3wgp`'s round 1.
3. **`14k9`: rebase before every round, merge one PR at a time.** The round-4 medium was not a header defect: "main has moved again with #92 ... src/components/app-shell.tsx has a real content conflict ... src/app/layout.test.tsx calls RootLayout synchronously while it is now async". A round spent on a re-merge is ~219k here, plus the implementer pass. Reduction: `wzgw` item 5, sequential merges with `main` green between, and a rebase-and-rerun gate before each review round. The post-cap scoped verification (not a counted round) was a further uncounted review pass.
4. **`akv6`: the same, with the bill for the three-at-once merge.** `#94`, `#95` and `#97` were merged within two minutes of each other on the morning of 2026-10-05; each was green on its branch and `main` went red (bd memory `sequential-cap-merges-broke-main`). `akv6`'s post-cap verification comment records the cost: "main at 2425355 really fails typecheck (TS2554 in site-header.height.test.ts) and the audit (hero.tsx text-ink), both green here" and "it also restores main's CI". The restore work sits on this bead's figures. Reduction: `wzgw` item 5 again, plus an identity change so the lows at rounds 4-5 (footer tagline wording, K2 string block) were filed rather than fixed in a fifth round and a verification pass.
5. **`6dvg`: comments point at tests; tests carry the measurement.** Rounds 1-3 each found one real medium by execution (text drawn over an opaque decorative circle at 360-1024px; an unguarded `await sessionPromise` that turned a session blip into a 500; a contrast pairing audited against the hex palette token while the page rendered the oklch one). Rounds 4-6 were entirely family 1: what an e2e motion spec's comments claimed to exercise, a `translate-none` sentence, a snapshot the PR body still disagreed with. Reduction: `wzgw` item 4, a fix round may not add prose beyond what the finding needs and a measurement lives in a test, not a comment; three lows-only rounds at ~198k each is ~594k, and under an `exact` chain the PR would have merged at round 4 with one low filed instead of three rounds later with one low filed (`quxl`).

For contrast, v0.4.0's top five (`jsc` ~2.1M, `egp` ~1.96M, `2yj` ~1.66M, `t0y` 1.5M, `j4j` 1.35M) were build-heavy: `jsc` and `t0y` recorded no review cost at all and their stories are scope ambiguity and in-review mechanism growth, already written up in `harness-cost-controls` section 6. v0.5.0's top five are review-heavy. The expensive failure mode changed between releases, from building the wrong thing to reviewing the right thing six times.

## 6. Recommendations for v0.6.0

### 6.1 Routing: bead type to tier and effort

Proposals to test, not measured results (section 1). Each row says which numbers above motivate it.

| Bead shape | Tier / effort | Why |
|---|---|---|
| Feature or fix touching auth, privacy, rights, payments, media storage, migrations (`cc_scope` auth, privacy, rights, media, upload API) | **opus / xhigh**, strict gate at every round even after the identity change | Opus rounds found the release's authz and data mediums (`t33p` 6, `mzr` 2, `ysub` 6); the two rounds-5-6 mediums in the whole release were both auth (`#81` r5, `#98` r6). |
| UI feature or UI fix (design, pages, gallery, a11y, upload UI) | **sonnet / high**, preceded by an execution pre-review (section 6.3) | Sonnet shipped every design feature at one medium per round for three rounds, each found by running the page; opus on `rw9j` shipped twelve contrast regressions, so tier is not the lever here, the gate and the pre-review are. |
| Fix that adds or changes a test, or any bead with a guardrail test | **sonnet / high** minimum | `o7l`'s two vacuous-test rounds on haiku; `e15`'s unlanded fix; `review-standards` family 3 is the repo's recurring defect and haiku has not cleared it once. |
| Mechanical change: one-line config, comment correction, gitignore, rename, docstring | **haiku / low-medium** | `4at`, `asg`, `e5zf`, `aj2k`, `r3h` all passed in one or two rounds at 8-58k build. |

### 6.2 Per-bead budgets and the stop-and-escalate rule

Budgets are set near the v0.5.0 medians for the shapes that went well and well under the medians for the shapes that did not, so that exceeding one is information rather than noise. "Stop" means the orchestrator posts what it has, files the remainder as beads, and hands the decision to Eirik; it does not mean the work is abandoned.

| Bead shape | Build budget | Review budget | Round budget |
|---|---:|---:|---:|
| Feature, UI | 900k | 800k | 4 |
| Feature or fix, auth/privacy/data | 800k | 1.3M | 6 (the strict cap) |
| Fix, behavioural | 400k | 500k | 3 |
| Fix mechanical, docs, chore, test | 100k | 150k | 2 |
| Investigation / judgement | 300k | 150k | 1 |

Stop and escalate when any one of these holds:

- **B1: round 4 is reached and only lows are outstanding.** Today this is the start of the lows-only tail (section 3: rounds 5-6 found a medium 13% of the time). Until the identity change makes round 4 a merge point, the orchestrator stops here and asks Eirik to merge with the lows filed, instead of running rounds 5 and 6 to reach the same decision two rounds later. This single rule would have removed ~22 rounds from v0.5.0's eleven cap PRs.
- **B2: three implementation passes without a clean round.** `jx4` ran six (2.0M). A PR that has not converged in three passes is being redesigned in review; redesign is a bead.
- **B3: a round at or after round 3 states three or more new mediums.** `3wgp` round 4 (four), `qnq9.7` round 4 (three), `ysub` round 4 (three): each was a PR whose premise had shifted, not a fix list. Stop, write the finding into the bead, re-plan.
- **B4: recorded cost passes 1.5× the budget** for its shape. With `tokens_impl` recorded as the subagent total and `tokens_qa` recorded per round (section 8), the orchestrator can check this between rounds without estimating.

### 6.3 Performance: fewer rounds, fewer defects reaching review

- **Pre-review on the branch, with execution, before the PR exists** (`wzgw` item 2). Round 1 blocked 25 of 35 PRs and found 15 mediums. The mediums on the design features were found by loading the page: contrast with the repo's own `color.ts`, a real 500 under a session failure, an overlap hit-test at 360px. The pre-review checklist should therefore include running the app (the `run` skill) against the branch for every UI bead, the `color.ts` contrast audit over plain utilities (the `rw9j` round-2 gap, still open as the Button-level contrast guard bead), the four-family sweep, a comment-claims audit, and `scripts/sweep-candidates.mjs`. Target from `wzgw`: round-1 finding counts halve; measure it as the round-1 "found ≥1 medium" count in this report's table dropping from 15.
- **Mutate the fixture, not only the production code**, for every new assertion (bd memory `mutate-the-fixture-not-just-the-production-code`, `ws3`). `o7l` rounds 1 and 3, `6dvg` round 5, `8df3`'s `it.fails` tripwire, `98` round 6's untested race branch are all family-3 findings a fixture mutation on the branch would have surfaced.
- **Rebase onto `main` and rerun the gates before every review round; merge one PR at a time** (`wzgw` item 5). `#94` round 4 and `#96`'s restore of `main` were re-merge costs; ~2 rounds ≈ ~490k plus two implementer passes.
- **Comments point at tests** (`wzgw` item 4). The lows-only tail is family 1. A fix round that adds a paragraph has added next round's finding.

### 6.4 Cost: routing, resumed reviewers, budgets

- **Identity change first** (`wzgw` item 1): run `pr-review-merge` under a bot account or GitHub App so chains read `exact`. Expected effect on v0.5.0's shape: 11 of 12 cap PRs merge at round 4 with lows filed; ~22 fewer review rounds and ~22 fewer implementer fix passes; a crude ~3.5-7.0M review tokens per release-equivalent (section 3). Keep the strict rule for auth-scoped beads (B1's exception) because both rounds-5-6 mediums were auth.
- **One reviewer per PR, resumed** (`wzgw` item 3). Median crude cost per round is ~106k on sonnet beads and ~164k on opus beads, paid for a fresh agent, worktree, `npm ci` and full re-verification each round even when the delta is one sentence (`ysub` rounds 5-6). A resumed non-fork agent keeps its worktree and transcript; `wzgw` K2 sets the target at under half a fresh pass. With ~60 delta rounds per release that is ~3M tokens.
- **Route by the table in 6.1**, and stop leaving the reviewer's model to inheritance: the review forks are the largest spend and the only place where tier choice has no record at all.
- **Budgets in 6.2**, enforced by the orchestrator, not by the reviewer: the reviewer's job is depth, the orchestrator's is to stop paying for it when the row says so.

### 6.5 Simplicity: fewer steps, locks, markers and hand-offs

- **One implementer and one reviewer per PR, both resumed.** Every round today is a hand-off chain: orchestrator → fresh implementer (new worktree) → orchestrator → review (five finder forks plus a consolidator) → orchestrator → verdict → implementer. The verdicts record what that costs beyond tokens: "verdict posted late because the consolidating reviewer did not report; the finder angles did" (`#81` round 5), "the `code-review` fork stalled with no progress for 600s" (`#78` round 5, `#77`), duplicate round-2 and round-5 markers posted by review forks that lost track of the orchestrator's verdict and had to be deleted (`#94`, `#97`), "a review worker ... review costs double-recorded on the bead by the same worker have been reversed" (`#94`). Finder angles as tool calls inside one reviewer agent, not as sibling agents, removes the consolidation step and the duplicate-marker class entirely.
- **Make round 4 the merge point and retire the post-cap choreography.** With an `exact` chain, the "scoped verification, not a counted round" comments (`#94`, `#96`), the "merge note" comments (`#101`), the cap escalation options (a)/(b) comments and Eirik's manual squash-merge of twelve PRs all disappear for non-sensitive paths. The per-PR lock (`refs/review-locks/`) and the `broken`/`approx`/reset machinery stay as written, because they are what makes the marker chain trustworthy and this very report reads the markers; but the self-asserted branch becomes dead code for new PRs and the skill text can say so.
- **Record what this report had to estimate.** Section 8.

## 8. What to record so the next report does not estimate

1. **`tokens_qa` per round.** `pr-review-merge` already has the exact `subagent_tokens` per run; record it as `tokens_qa_r<N>=<n>` beside the accumulated `tokens_qa`, so the first-round/tail split in section 5 stops being a mean.
2. **`tokens_impl` as the subagent total, always**, with `tokens_impl_passes=<n>` so B2 is checkable. "Rough estimate, inline in the orchestration session" is the current state of 14 v0.5.0 beads.
3. **The model that ran**, as `model_actual=<tier>` on the bead when the orchestrator spawns the implementer and reviewer with an explicit `model`, since that is the one fact section 4 cannot read today.
4. **`release` on every listed bead at cut time**, and the leaf bead id in every PR title.
5. **One bead per PR, or `cost_on=<bead>` on the siblings** of a shared PR.

## 9. Reproducing the tables

```bash
# From the repo root, with gh authenticated and bd available.
node scripts/release-cost-report.mjs --releases v0.4.0,v0.5.0 \
  --cache /tmp/release-cost-report-cache \
  --write docs/process/release-cost-v0.4.0-vs-v0.5.0.md

# Offline re-run against a saved bead export and the same cache:
bd list --all --json > /tmp/beads.json
node scripts/release-cost-report.mjs --beads /tmp/beads.json --cache /tmp/release-cost-report-cache --offline
```

The script exits 2 if any bead in either release lists a PR in `prs` that is not `MERGED` (K3). It reads round markers the way `pr-review-merge` step 4b does (first line only, anchored, CR stripped, pages flattened once after `--paginate`), classifies severity from the reviewer's words, marks estimates with `~` from the beads' own notes, and rewrites only the block between the two HTML markers below. `npm test` runs `scripts/release-cost-report.test.mjs` over the pure parts (membership parsing, estimate marking, median, chain reading, severity classification, close-reason rounds).
